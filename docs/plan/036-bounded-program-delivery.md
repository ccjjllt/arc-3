# 036：有界程序交付与受检执行

日期：2026-10-22，北京时间。起点为 `55d4d54f890afc12ed0603f682a8f6b734492fd1`。035 在既有交接中保留给区分性探测；本轮沿 034 的程序修订方向单独编号。当前正式最佳为 009 v2 / submission 57101330 / public 31.16。

## 背景与问题

034 v2 的两个辅助请求输入分别为 61,612 和 89,613 tokens，均输出 4096 tokens，只有 reasoning，没有工具调用。可执行代码、通过验收的程序、宿主计划动作、预测检查均为零。su15 的额外一关发生在普通主循环，不能作为程序修复有效的证据。详见 [034 结果](../../research/034-v2-results-analysis.md)。

源码中存在一个明确的请求控制缺口：`program_repair._completion` 继承主循环 thinking 设置，而 034 用相同的 4096 completion 上限要求生成完整程序。原基线支持请求级 `enable_thinking` 覆盖；辅助分支没有利用它。同时，分支复制整段历史，重新附加当前代码和观察，而没有按局部任务选择材料。

033 的反事实说明准确像素进入已有目标程序后，在指定切点可以自动产生两次点击并过关；但这只是研究者干预。030/032 的公开开发收益也没有转化为正式增益。因此本轮要分别回答代码交付、真实程序消费和同预算得分，不能用任一中间指标代替最终成绩。

## 目标与可证伪假设

主假设：辅助请求只携带当前程序、必需依赖、最新观测、近期动作和短的规则假设，并关闭该请求的长思考、明确要求一次 Python 工具调用，可以在相同 4096 输出预算内交付可运行程序；宿主沿既有验收和动作路径消费这些程序后，能够增加同预算的实际推进。

第一项成立而第二项失败时，结论只能是交付问题改善，不能称求解算法或正式分数已经改善。最终目标是获得一次真实、可追溯的新 competition submission，并由 COMPLETE 的 public score 判断是否超过 31.16；不预先承诺分数或排名。

## 候选实现

新模块为 `src/arc3_research/bounded_executable_plan.py`，通过 `install_bounded_executable_plan()` 安装。自然研究、同状态诊断、保存验证和正式 rerun 使用同一模块及默认参数。

1. 请求级覆盖 `enable_thinking=False`、`preserve_thinking=False`、`tool_choice="required"`、`parallel_tool_calls=False`；只暴露一个短 Python schema。普通主循环的 thinking、模型、采样和调度不因该覆盖而改变。
2. 以暂停代码引用的名称构造保留函数的依赖闭包，附完整源码；携带最新 ASCII 帧、合法动作、最近真实动作、必要反例与既有计划。最近模型判断只作为未验证假设，不能冒充环境事实。
3. 请求上限冻结为 32,000 字符和 64,000 UTF-8 字节，假设文本至多 1,600 字符。完整必需代码或观察无法容纳时退出辅助请求，不截断半个函数，也不执行不完整代码。字符上限不是 tokenizer 的实测 token 上限。
4. 维持原有零动作验收、当前帧像素核对、确定性重算、逐动作预测、失配停止、函数回滚以及单次建立/单次后续修复配额。
5. 记录真实请求控制、输入范围与源码 hash、finish_reason、usage、耗时和失败阶段，区分未返回代码、格式拒收、执行失败、合同拒收和真实动作后的预测失配。

辅助请求继续使用 4096 输出 tokens、60 秒单请求、120 秒共享额外处理预算；剩余时间不足 180 秒不启动。关闭辅助思考是待验证选择，不使用未核实的数字型 thinking_budget 参数。原 034 默认路径保留，036 显式安装新请求构造方式。

## 实验安排

### 同状态诊断

复用已冻结的 ft09 cut27 与 su15 cut86，A 为原样续跑，B 为新辅助分支后续跑；每题 450 秒、60 动作，两题并发。每臂 runner 600 秒，启动上限 4200 秒，Notebook 总上限 7200 秒；臂间清缓存最多等待 120 秒。两臂恢复到相同帧、历史、函数和动作前缀，修订时间计入原续跑预算。

这两个切点也有明确局限：ft09 没有保留规划函数，su15 主要是动作与检查 helpers。因此分别说明程序构造与现有控制代码修订的成分，不把结果泛化为任意规划器修复能力。首份真实响应须确认当前挂载模型模板确实遵从请求级非思考设置，且产生完整工具调用。

诊断观察完整链条：请求返回 → 完整定义 → 验收 → 当前目标重算 → 实际动作 → 预测检查 → 新增关卡。仅有代码、注册或 match 不构成扩大的充分理由。若依然没有可消费程序，或修订只是增加耗时且不改变错误行为，停止该版，不重复同一配置。

### 一次自然全 25 题比较

在诊断得到可解释的真实消费后，冻结候选，从游戏起点比较 baseline 与 bounded_executable_plan。25 个游戏完整保留，每臂 7254 秒、10 active streams、1 pass、warmup 1，同一模型服务、相同题序、独立求解进程；辅助费用包含在该臂预算。启动上限 4200 秒，Notebook 总上限 21600 秒，cache wait 120 秒。

主指标为相同 SDK 公式的 25 题平均分。逐题/逐关完成、动作、时间和 token 用于解释；完整保留最大涨题和最大跌题，不事后筛题，不要求每个辅助指标都同时上涨。历史 005/027 基线仅提供波动背景，不能替代同期对照。一轮正差也不能宣称稳定泛化。

自然触发沿用 034：首次符合条件的多动作或同一代码调用第二次动作可能触发，并非只在已经证明失败后触发。这会打断原本有效的计划，是同预算比较必须观察的成本。不得把人工切点的触发覆盖当作自然运行覆盖。

## 已知语义风险

- 原预测合同允许只选择少量像素。只预测不变背景也可能得到 match，不能把它称为整体动力学正确。记录预测覆盖与变化像素，人工对照动作相关对象和实际推进；不以 match 数为主指标，也不简单禁用所有合法的 no-op 预测。
- 非思考输出可能格式更可靠但算法质量下降；压缩历史可能丢失早先规则证据。两者都需要真实模型结果，不能由本地构造成功推定。
- 当前 bootstrap 可能在正常解题中触发，新计划可能比原计划差。保留失败恢复及预算边界，记录被打断的动作与最终结果。
- 公开题池已反复研究；隐藏逐题日志不可用。正式负结果不能事后无证据归因于某个运行或记忆问题。

## 保存、正式运行与提交

正式构建从冻结 009 原生 Notebook 出发，只安装同一候选 helper，不包含切点包、公开题目答案、研究 fork runner、030 持久状态或 032 记忆。正式模式仍由平台提供 `KAGGLE_IS_COMPETITION_RERUN`；通过 COMPETITION gateway 动态读取环境，提交文件由平台生成。

另有一项明确记录的运行修正：从第一 cell 记录总时钟，将 32400 秒上限扣除已耗时和 300 秒收尾预留，给正式 `bm.run` 设置 soft deadline，并把每游戏最大时间限制到剩余额度。009 的 formal soft_end=None 未扣除全部冷加载开销；本修正不被包装成程序修复的算法收益。平台在第一 cell 之前的准备耗时仍可能不可见。

候选自己的保存验证维持真实模型加载、health 成功及 sb26/cd82 两题各自出现真实非 RESET 动作与生成 token。求解窗口仍为 300 秒；启动等待上限改为 4200 秒，总保存上限 5400 秒，以容纳近期观察到的长冷启动。只有此验证完成后才生成官方未计分占位文件，不能把占位文件或 Notebook COMPLETE 当成正式分数。

运行前读取实际账号与团队、当前 GPU 可用额度、当日提交额度及输入可见性；历史快照和配置中的 owner 不作为实时授权状态。冻结成功保存版本后，以准确 kernel/version/file 创建正式 submission，归档 ID、状态与 public score。只有实际超过 31.16 才更新已知最佳，否则保留 009。

# 006 — 同池A/B数值结果与解释边界

分析日期：2026-10-11（Asia/Shanghai）。范围为已完成的006公开OFFLINE诊断实验，两组各12游戏、1遍。本次仅CPU读取原始输出和复算，没有新GPU、没有测试文件、没有执行模型轨迹代码。

## 当前结论

baseline **28.3856分、36/91关、3个全通**；transient_history **21.9216分、31/91关、1个全通**。干预组低 **6.4640分、5关、2个全通游戏**。本轮没有支持晋升为默认策略或扩大运行的总体收益证据。

这次机制确实执行：干预组101次Python工具返回附加了246条历史暂态事件，区别于003的0次nudge。但附加成功不等于模型采用，不能只凭总体分差断言暂态信息必然有害，也不能仅看tn36的改善就声称研究假设成立。特别是最大正差m0r0和大幅回退ar25都没有任何附加事件；共享调度和生成路径波动仍不能忽略。

本报告只比较006内部同12游戏，不与005全25或003原16均值直接比较。

## 附加事件分布及限制

干预日志统计：1,016次被观察的Python调用，514次无新增环境动作，401次没有可附加的较早暂态，101次实际附加。捕获640条暂态；其中229条是末动作已有渠道，76条在终局/RESET边界或之前，335条符合非末动作条件。限长后附加246条、明确省略89条，总新增文本95,100字符，单次最多1,346字符，未超过1,600字符上限。

没有`observation_read_error`、`missing_before_frame`等失败状态。日志新增真实动作2,065，加benchmark中的14次RESET恰好等于2,079动作；逐游戏也全部吻合。baseline日志为disabled、calls_observed=0，是补丁未观察的预期值，不是baseline没有执行Python。

| 游戏 | 附加所在关卡（次数） | 主要解释限制 |
|---|---|---|
| tn36 | L2一次、L3一次、L4一次 | **L1没有附加**；不能把首关路径改善归因于006文本。首次附加绑定action33，before32→after34，已在L2。 |
| sc25 | L1一次、L4四次 | 总计仅6事件；需比较具体动作与后续计划，不能凭整局回退归因。 |
| bp35 | L1五次、L2十二次 | 仍只完成1关；更多动作和更少尾推理不等于新增覆盖。 |
| sk48 | L1六次、L2一次、L3七次 | 整体少过1关；存在附加后的进一步动作，不自动构成采用证据。 |
| lf52 | L1一次、L2二十一次 | 123个候选附加65、省略58；高重复观察是否帮助或分散注意需读轨迹。 |
| su15 | L2十二次、L3五次、L4十一次 | 增加1关，仍需确认读到具体旧动作事实后如何改变推理。 |
| g50t | L1十二次 | 一关未过；不能以“附加较多”当成剂量效果证据。 |
| sp80、wa30、m0r0、ft09、ar25 | 无 | 仍有显著正负差，暴露分组不是随机对照。 |

尤其m0r0是最大正项却0附加，ar25是第二大负项也0附加，ft09的效率改善同样0附加。它们不能证明文本有利或有害；也不能说这些游戏完全不受实验臂影响——额外runtime读取开销、共享GPU调度、其他游戏的轨迹变化，以及随机采样都可能影响其计算机会。仅凭日志不能分解这些因素。

95,100字符是首次写入工具结果的长度，不等于真实累计prefill开销：历史可能多次重发且有cache。不能用“没有显式新增LLM调用”推断补丁没有任何资源代价。

## 预算、停止与版本一致性

| 项目 | baseline | transient_history |
|---|---:|---:|
| 请求有效预算 | 3,482秒 | 3,482秒 |
| benchmark JSON起止时长 | 3,497.934秒 | 3,504.257秒 |
| 包含诊断输出的benchmark墙钟 | 3,500.625秒 | 3,506.937秒 |
| arm进程墙钟 | 3,503.081秒 | 3,508.358秒 |
| 尾部analyzer timeout日志 | 7条 | 10条 |
| 截止后环境动作 | 0 | 0 |
| 截止后完成关卡 | 0 | 0 |

两组都触发共同soft deadline；9/11个cancelled是预算截止上下文，没有crashed、未启动游戏、强制CPU退出或遗留worker。动作层RESET有13/14次，应与run层截止分开，不能把RESET一概当作程序失败。工具内部Python错误仍须逐轨迹读，本报告没有宣称不存在此类错误。

按`started_at + history.wallclock_seconds`与soft_end对齐，并用每关动作数恢复完成动作，两组所有得分动作和完成事件都在有效预算内。超出的约15.93/22.26秒是观测到的收尾时长，不是多执行动作得到的优势。timeout日志都位于集中收尾区，read timeout小于常规900秒；不将没有game_id的日志强行逐条归属。

已核对两组以下内容完全一致：12个完整版本ID与顺序、game_order_sha256、OFFLINE模式、3,482秒预算、10条active streams、12个逻辑并发任务、1pass、warmup0、900秒analyzer timeout、source_sha256、记录的environment。CPU PID不同；服务日志确认两次`Cache flushed successfully!`。干预代码hash为`a90295262d8125f6d33e5f42a9ba992ced9a96c820db38ea5d4bd231bc70114c`，runner为`d34e129a96ef6863612b5787761915ed066a25282bf885022535cc3af88bee95`，两组相同，仅安装开关不同。

runner总用时7,560.388秒（约2.1001小时），模型ready花539.892秒，末尾已停止GPU服务。它不包括所有Notebook外层开销，账户计费以主任务查询为准。baseline固定先运行、第二组共用已编译kernel、采样温度0.7且没有独立重复，因此即便以上条件一致，仍不构成独立配对的因果估计。

## 研究交接

本轮足以判断“此版本暂无总体收益，不应直接晋升或扩大”，不足以判定保留历史暂态这个方向必然无效。先深读同轮两组tn36、sc25、ar25，及m0r0正向变化对照；必要时补lf52/g50t的密集附加与回退案例。

需要确认的是：模型是否读到**指定旧动作号**、是否据此纠正了“无效动作”的推断，以及后续规则探测/过关发生在附加之后。只计附加条数、API名称或整局得分不能替代这条证据链。对L1零附加、整局零附加、附加后尚未改善的情形分别记录；没有观察到采用不等于理论机制不存在作用，但也不足以追加同样的GPU运行。

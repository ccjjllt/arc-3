# 006 — 保留非末动作暂态，避免观察被后续动作覆盖

日期：2026-10-11（Asia/Shanghai）  
对应进展：[006-transient-history](../progress/006-transient-history.md)。  
继承：[005结果](../progress/005-full-baseline.md)、[004复核](../../research/notes/004/004-review-data.md)。

## 背景与单一假设

005全25为49.8997分/106关，当前完成集合的动作效率空间仅0.4764分。tn36首关轨迹提供一个具体的信息交付缺口：同一Python片段连续调用action()，较早按钮的最终棋盘不变；模型只打印no_op等字段，随后动作覆盖了默认last_animation和user摘要。模型据此把按钮当成无效，转向对1024状态的目标猜测。

独立CPU复现已确认：005的前缀及全部5个动作末帧与保存画面一致；非末按钮返回7帧、256暂态像素，后三探测无暂态。详见 [复现记录](../../research/notes/005/005-animation-replay.md)。这是公开SDK复现，不是恢复005历史中间帧，也没有求解收益结论。

底座并未删除全部元数据：真实history entry.result仍保存每个动作的animation、action_num与完成/死亡标记。缺口是这些较早动作的暂态事实没有自动进入当前工具反馈；不需要重新发明动画API或让模型自报marker。

**假设：** 将本段Python中非末真实动作的短暂态记录自动附在现有工具返回，可减少“结算帧不变→动作无效”的误判，改善后续规则探测与关卡覆盖。现有轨迹和CPU复现只能验证信息通道，不能证明提分。

## 具体实现范围

新增 src/arc3_research/transient_history.py，沿用opt-in wrapper方式。对每个游戏独立状态：

1. 在原_run_python_tool调用前读取当前真实step，原调用完成后读刷新后的runtime history。
2. 只处理本次新增且executed的真实动作。绑定实际action_num、动作描述和前后level；不按代码字符串推断是否执行。
3. 补充非末动作中transient_pixels>0的动画元数据，排除自动RESET及通关/死亡转场。既覆盖多次action()，也覆盖单次action([...])中的真实中间动作。
4. 每段最多保留4个事件，超过时明确计数；只保留帧数、暂态格数、bbox和真实动作号，限制附加文本长度。显示为本段较早动作的历史事实，不能暗示last_animation_frames仍指向它，也不能宣布游戏规则。
5. 末动作已有反馈保持原样；保留dispatch的step_executed/made_progress等标记，不执行额外动作、不新增LLM调用、不依赖模型marker、不按game ID写解法。
6. 记录捕获、筛选、实际附加事件数及game/state_path/step/level。实例未触发不等于策略无效；附加成功也不等于模型采用或提分。

修改 run_arm.py 新增单独arm，baseline不启用；build_experiment.py继续显式配置生成新目录，原003/005保留。截止后请求问题与本策略分开记录；若在本轮同时修复，应两组使用同一资源修复并明示，不能算作观察策略收益。

## CPU实现与手动检查

先用已有真实history元数据或公开SDK手动动作复现，确认中间动作的元数据在后续动作后仍可提取，并正确绑定动作号。局部SDK复现不是恢复005历史中未保存的帧；必须分开标记。

人工检查多调用、动作列表、被拒绝/跳过动作、自动RESET、转场和无暂态情况；使用手动命令或真实轨迹，不新增测试文件。检查附加输出长度及不同游戏状态不串用。不要执行日志内模型生成的整段代码。

## 观测与决策

机制：非末动作事件是否真实附加，模型是否注意到该历史事实，后续是否重新探测/立即读帧，错误“无效动作”判断是否被修正。逐例读取真实推理和动作，不能只计API关键词。

效果：主要看完成关卡/游戏和均分，附带token、动作、首次未解关、求解GPU利用率与实际时长。保留所有回退，尤其sc25和成功规划对照。若只增加文字而没有改变行为或覆盖，不扩到全25；若触发0次，先查覆盖条件，不原样追加GPU。

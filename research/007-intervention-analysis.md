# 007 program_state：实际触发与后续行为

本轮确认了补丁的局部功能：没有新函数快照的 Python 超时发生后，旧函数可以继续调用。尚未证明它提升完成关卡数或得分。三个反馈均在后续原始模型请求中出现；两次保留非空函数集合的事件均有随后成功调用旧函数的证据。

分析只读取 007 v2 的原始 requests/events、诊断和 benchmark，不执行模型生成代码、不重跑游戏、不消耗 GPU。可核对的选段、物理行号、函数定义/调用名和源文件 SHA-256 见 `experiments/007-analysis/intervention-traces.json`。

## 1. 触发范围

`program_state/program-state.json` 记录 1,039 次有效快照透传、3 次缺失快照，均为 30 秒 Python 工具超时。其中 2 次保留非空集合，合计 38 个函数出现次数（21 + 17，不能当作 38 个独立成功案例）。三个事件只发生在 re86、ls20；其他十个游戏没有触发。

| 游戏与事件 | 超时结束位置 | 旧函数数 | 后续 request 物理行 | 观察结果 |
|---|---:|---:|---:|---|
| re86 首次 | action 58，L3，analysis step 10 | 0 | 39 | 收到提示，下一次重新定义 ring/xsh；没有旧函数可挽救 |
| ls20 | action 329，L3，analysis step 32 | 21 | 151 | 直接调用旧观测函数；随后 5 步完成 L3 |
| re86 第二次 | action 325，L6，analysis step 38 | 17 | 147 | 后续直接调用 lines/Wpos 成功；L6 未完成 |

表中 request 行分别来自 `program_state/re86-8af5384d_p0_requests.jsonl` 和 `program_state/ls20-9607627b_p0_requests.jsonl`。request 的 `action` 是下一动作索引，所以记录值 59/330/326 与已执行 action_num 58/329/325 相差 1，不应混为一谈。

三个 request 中的 tool 消息确实带有 `This call returned no function snapshot...`，不是只写进旁路诊断。消息说明保留最后提交的函数/import 集合，失败调用中的新定义和改动不保存，已执行动作不回滚。这里只实证了旧函数可执行，没有单独验证 retained imports 的效果。

## 2. ls20：保留后确实继续使用，最终通过的是已有路径上的 L3

原始事件 `program_state/artifacts/ls20-9607627b_p0_events.jsonl:382` 记录超时：模型在一个 Python snippet 中反复 BFS 重规划并逐步执行，已执行 36 次 action 调用，最后到 action 329、L3，没有过关或死亡。本次新定义 `freemap`、`bfs`、`state_idx` 没有成功提交；此前 21 个函数保留下来。

下一次模型调用没有重新定义任何函数，直接调用 `macro3`、`icon_state`、`nook3`、`budget`、`build_map5`。原始 request 行 153 的工具反馈已打印：

```text
pos (2, 9) icon ('b', 'b.b/..b/bbb') nook b.b/b../bbb budget 18
plus cell B yellows [] (1,10) . (2,10) .
```

这证明旧函数实际运行；同一调用稍后出现 `AttributeError: 'HistoryEntryView' object has no attribute 'step'`，原因是读取 history 时用错接口，不是函数丢失。因此不能把这一整次调用笼统记为“成功无错”，也不能因末尾异常否认前面函数已经成功执行。

随后两个调用均未重新定义上述旧函数：

1. request 行 155：用 `macro3` 重读历史、用 `icon_state`/`budget` 检查状态，执行 RIGHT、LEFT、UP、RIGHT，到 action 333。颜色和图案匹配，但被活塞推到入口后尚未过关。
2. request 行 157：再执行 DOWN，工具返回 `LEVEL COMPLETED`。对应 events 行 388，action 334、analysis step 34，完成 L3、进入 L4。

这是“超时后保留的代码帮助延续正在进行的求解”的直接链条，但不是分数增益的反事实证据：baseline 的 ls20 原始 125 个 request、124 个可见去重工具结果中没有 Python timeout，L3 在 action 205 已完成，最终完成 4/7；program_state 最终为 3/7。B 在首次触发前完成 L2 就用了 197 个动作，A 为 114，路径差异已经存在。

## 3. re86：一次空集合提示，一次非空保留，但没有新增完成关卡

### 第一次：空集合，没有实际旧函数保留收益

events 行 71 记录 action 58、L3 的纯计算超时，没有执行动作。模型试图枚举几何形状，候选搜索过大。本次函数 `plus`、`xsh`、`ring` 未提交；之前提交集合为空。

request 行 39 收到保留 0 函数的消息。下一调用（其反馈在行 41）主动重新定义 `ring`、`xsh`，缩小搜索范围，打印找到的几何形状。此后确实完成 L3（action 105），但不能把这归为旧函数保留的贡献。

### 第二次：旧函数继续运行，几何解释仍未解决

events 行 379 记录 action 325、L6 的纯计算超时，原始 request 行 147 收到保留 17 函数的反馈。本次新定义 `tcells`、`scells` 未提交。

随后轨迹：

- 行 149：一次不完整代码导致语法错误，尚未运行 sandbox 代码。
- 行 151：重读 segmentation 成功。
- 行 153：重新定义简化后的 `tcells`、`scells`，打印 `n sols 0`。这里重新定义的是失败调用中的新函数，不是被保留的旧函数。
- 行 155：执行 5 个 LEFT 后直接调用旧 `lines(a)`，成功返回观测结果；中间没有重定义 `lines`。
- 行 159：直接调用旧 `Wpos()`、`lines(a)`，打印选择位置与几何数据；中间也没有重定义它们。

因此非空保留机制确实生效，但之后至最终 action 351 没有新 level completion，B 仍为 5/8。记录也暴露出另一种研究问题：`lines` 将同一行同色目标点与形状的极值范围混在一起，模型一度把包围范围解释成连续延伸的线段；后来读取 segmentation 的 40 像素对象时才发现与这个解释矛盾。保留可执行代码不等于保留了正确世界模型，也不能由本例证明“保留坏函数导致失败”。

## 4. baseline 中的真实反例与恢复成本

baseline re86 的 request 行 121 明确显示一次 30 秒超时后 14 个旧函数被清空。events 中超时结束于 action 434、L5；该调用执行了 29 个动作，属于反复 LEFT/RIGHT 消耗动作额度的循环。

下一调用（反馈行 123）主动重定义 `bar`，打印剩余预算，改成一次 batch 执行 40 动作，成功运行。之后又重定义 `objs` 等观测函数。可观察到代码重建与策略调整，但没有紧接着的旧函数 NameError，也不能把所有后续推理都计为丢失函数导致的额外成本。A 仍在 action 564 完成 L5，最终也是 5/8。

这支持“缺失快照会实际清除旧函数”的原问题，但同时说明原模型有恢复能力。A/B 的超时发生于不同关卡、不同代码和不同已执行状态，不构成同一超时情境的对照。

## 5. 研究结论与下一步取舍

- **代码行为已确认**：三个反馈被真实请求接收；两次非空保留都随后调用了旧函数，无需重定义。
- **研究效果未确认**：ls20 的局部恢复没有转化为比 A 更多的完成关卡；re86 两臂均为 5/8。其余十个游戏零触发，不能把其分差直接归因补丁。
- **不据此推广为得分方案**：本轮只能支持将修复保留为可选基础能力，不能支持把它作为已验证增分项或金牌路线。
- **后续研究重点**：相比再消耗一整轮 GPU 验证这个低触发率分支，已有日志更值得研究的是结构化感知是否把目标点、可控形状与它们的外接范围混淆，以及如何用一次短探测修正错误几何模型。这里只提出从轨迹得到的研究假设，不宣称已验证解决方法。

# 010 — 本地轨迹诊断：分清缺少历史观察与没有用好已有证据

日期：2026-10-13（Asia/Shanghai）。只读取 005/007/009 已保存公开环境观察、请求与代码文本；额外下载了既有 005 的 cd82 请求及 events。没有启动 GPU、模型、游戏引擎或动作，没有执行轨迹中的模型代码，没有修改 008 原型、009 Notebook 或研究 runner。

## 结论

**不要把 009 smoke 的 cd82=0 分当成基线退化，也不要据此立即改调度。比较两条路线后，下一项 CPU 工程研究优先“按精确动作引用检索旧动作的完整动画”；cd82 的控制状态表/证据复用保留为独立备选，现有 008 全区域 JSON 工具也不直接上线。** 这是候选优先级判断，不是已经找到提分方案。

依据是 cd82 两条轨迹都已拿到足够清晰的像素、动作和差分，却花费大量推理反复重述不一致的控制理论。009 中一处所谓的 segmentation 错误实际是模型误记了正确 stdout；新增 mask 并不能保证修复这个环节。005 的成功过程也出现同一问题，后来开始枚举已观察姿态与控制关系并继续探测才完成首关。CPU 可以验证事实记录与查询合同；不能证明一条提示或一个辅助表会被模型采用，更不能证明新增通关。

旧动画路线的优势是存在明确的接口信息缺口和可检验的存取合同；cd82 路线的优势是直接指向错误证据使用，但缺少“新增工具提供了原来不可得信息”的证据。当前 008 有更清楚的“提取正确性”证据，仍值得保留，但模型选择区域、自动拆长面板和约千字符单区域输出成本均未解决。三者不要叠加到第一次实验。

## 能定位的机制

### 信息已正确交付，但使用不稳定

009 events L4：工具输出明确显示灰色框为 30 像素；ASCII 最后一行只有两端灰色像素，模型却在推理中把它叙述成上下都封闭的矩形，算出 42 像素后用“whatever”放过矛盾。这不是工具缺失该区域。

009 events L34：`stamp_state()` 在 RIGHT 后正确输出灰框 `(g,30,45,53,25,38)`，即行 45–53、列 25–38。L35 模型却声称此前得到的是 43 像素、行 30–45，并把不一致归咎于 segmentation 的边界极值；随后的 ASCII 和自行重写的 `read_state()` 再次得到原本已正确的 `(45,53,25,38,30)`。本次独立逐像素扫描也得到完全相同的正确范围。

这里需要改善的是事实复用和对模型自身摘要的核对，而不是再提供一份包含同样 bbox 的更长数据。可以增加工具来降低误抄概率，但不能把“输出更多正确信息”当作已经解决。

### 控制取决于当前姿态，模型却反复寻求单一正负旋转解释

009 L25/L31/L34 已观察到不同位置上方向键的不同效果。L35 与 L42 仍长篇尝试统一为固定 CW/CCW、重力、3D pitch/yaw 等理论，明知叙述矛盾后继续扩展理论。到 L38，它已验证下方姿态的 SPACE 能正确涂底半部，当前明确子目标只剩返回上方并覆盖多余颜色。

005 也有同样错误：L39 把已有几个左右探测归纳成“只存在三种姿态”，L44–50 为所谓不可达区域不断改写目标解释；L55 的 DOWN 才直接否定该范围假设。L73 开始明确列举观察到的姿态及转移，发现下方还有未测的 UP；后续完成首关。这个历史成功不是对“增加表格”干预的受控验证，但给出了值得测量的具体采用链。

CPU 诊断仅用当前保存帧中的灰色像素，独立计算位置与形状，按实际动作记录边：005 首关有 7 个已观察灰框姿态、20 条不同的箭头转移；009 有 6 个姿态、13 条转移；已观察边在各自投影下没有冲突。009 结束时图上仍没有完整已观察返回路径，不能凭 CPU 图声称已经找到可执行解法。未知边必须保持未知，不能把 005 未来观察注入 009 较早状态。

## 状态表不能靠粗糙自动化硬塞进去

009 的 27 份初始/动作观察有 23 个不同全帧；诊断性去掉最后一行后仍有 11 个不同画面，而灰框姿态只有 6 个。005 相应为 54 份、46 个全帧、20 个去末行画面、7 个灰框姿态。HUD、画布颜色、当前墨色与操纵姿态是不同因素。

本分析用灰色像素只是该公开病例的研究者投影，不是生产规则；通用 agent 不得写入 `g`、坐标、游戏 ID 或已知旋转解法。灰框投影对箭头控制有描述作用，对 SPACE 的绘制结果会遗漏画布和墨色；即使当前边一致，也不证明没有隐藏状态或时间依赖。原底座 `_state_identity_border()` 注释已说明默认全帧匹配的理由：随意忽略 HUD 会把不同真实状态合并，导致错误永久阻断。

因此第一次候选不应重写调度、启用基于近似 hash 的动作禁令，或尝试从任意全图自动建立确定性模拟器。

## 优先 CPU 研究：旧动作完整动画按需检索

现有接口核验：`HistoryEntryView` 与 `TransitionView` 只暴露 settled `frame`、前后帧和 `result`；`last_animation_frames` / `last_animation_timeline` 在每次动作后失效刷新。`tool_agent.py` 的 `_handle_animation()` 只向 callback 请求 `query=animation`，没有 action ID 参数；`_last_animation_chain` 也被最新动作覆盖。这不是模型少写一个 `history[-2]` 就能恢复旧中间帧的问题。来源：[sandbox](runtime-bundle/src/ARC3-Inference/inference/agent/python_tool_sandbox.py:182)、[动画查询](runtime-bundle/src/ARC3-Inference/inference/agent/tool_agent.py:5765)。

病例来源：[005 动画复现](005-animation-replay.md)、[006 采用与误用分析](006-intervention-analysis.md)。计数是 1 个直接缺口复现 + 2 个支持性信息不足 episode + 1 个独立归属错误，不是四个受控提分实验。

与 006 必须严格区分：006 只自动追加较早动作的 action_num、frames、transient_pixels、bbox；源码明确注明 `last_animation_*` 不能读取这些历史记录。B 实际追加 101 次/246 条/95,100 字符，有送达和部分采用，但总体净负。新方案不再自动把多条元数据塞进每次输出，而是保留 SDK 已产生的原动画链，只在模型按精确引用请求时返回帧或 timeline。它测试的是“需要时能读回旧证据”，不是再测试“多提示模型注意有动画”。

最小接口合同：每条记录绑定 game/session、episode/reset 序号、level-before/after、真实 action_num、动作参数、帧序；查询必须返回被请求动作的记录和原标识，不得悄悄回退到最新动画。同坐标不同 action ID 是不同记录。没有保存、已淘汰或跨 session 引用需明确 unavailable。持有记录本身不自动变成 prompt 内容。

CPU 验证先用已有保存的原动画/旧复现链，以及独立构造的小型链检查：同一 snippet 多次 action 后前几条仍可准确读取；latest 和 archive 互不覆盖；batch 内每个真实动作独立编号；RESET/关卡边界不串号；单帧/空动画/淘汰返回明确状态；关闭开关时行为与原版一致。旧记录的前后端点必须与已保存 event 一致，并保留源 hash。若当前存档没有某次完整链，不得用最终帧或未来样本伪造该历史记录。

容量应显式受限并计量。可从“每游戏最近 32 条动作、总计最多 256 帧”作为 CPU 工程起点；64×64 uint8 原像素约 1 MiB/游戏、110 游戏约 110 MiB，**这只是紧凑字节的下界估算，不包含 Python 容器、索引、序列化副本**。正式实现需测实际 RSS/字节并处理单条过大链，不把这个初始容量当作最优值。淘汰时应让模型知道记录已失效。

后续 A/B 单一开关只控制历史动画归档/查询和最少工具说明；不启用 006 自动摘要、不启用 008、不修改提示策略/调度/模型。先记录 archive coverage、request hit/miss、retrieved action 是否正确、模型是否引用/从中提取新事实、是否改变下一步探测，再看通关和资源。没有查询或只有重复信息应停止扩跑。具体游戏池和 GPU 预算由主任务结合所有候选决定，本报告不发起作业。

## 独立备选：控制关系使用说明

如果先验证 cd82 路线，第一版只替换/补充一段通用的控制证据使用说明，不新增画面输出、不加 008/旧动画、不改 serving、温度、调度或预算。其研究重点是模型采用，未证明有效前保持正式 009 为参考。

建议语义为：遇到动作效果随观察状态变化时，用当前可见特征记录小型 `state → action → observed next state` 表；未知转移明确保留未知；解释与结果冲突时优先保留结果并补一条可区分的短探测；已经足以推进当前子目标时执行已证实的路径，不先要求一个统一的几何理论；投影碰撞或同一输入出现不同后继时拆分状态并保留冲突。表及提取函数应留在已有 persistent Python functions/局部记忆机制内。

这与笼统的“多验证”提示相比，有可以在日志里判断的对象和动作，但仍可能不被采用，或诱导模型在不需要状态表的游戏里浪费时间。不能把提示已出现在 system prompt 当作机制触发。

CPU 前置验证范围：

1. 用 005/009 保存观察验证状态记录、箭头标签、后继记录、重复/冲突与未知边查询；不补任何尚未执行的边。
2. 正例与反例一起保留：同 pose 不同墨色/画布对 SPACE 不等价；仅有像素重复不等于隐藏状态重复；不存在路径时必须返回未知。
3. 只把派生表作为研究者诊断材料，不自动加入模型早期上下文；在线模型需自行选取当时可见的投影。

GPU 若继续，仅跑匹配 A/B，建议首轮 8 游戏包含 cd82、tr87、re86、sb26、ft09、tn36、lf52、sc25；cd82 是机制病例，tr87/re86 是表示瓶颈区分病例，sb26/ft09 为已能成功的副作用检查，后 3 个覆盖当前低分区。两臂同池、顺序、总预算与原基线约 290.16 秒×游戏数的归一化一致，一次模型加载；单遍只用于筛选。首先检查是否实际构建并查询表、是否纠正已观察矛盾及选择新探测，再看新增关卡、动作/token/墙钟和回退；无实际采用先修机制，不因一个游戏随机上涨晋升。预算和账户配额须由主任务另行确定，本报告未启动实验。

## 与 008、调度和 actor 建模的比较

- **008：** tr87 的错误裁剪、旧缓存、ASCII 编码坍塌是可复现的直接问题；re86 的杆坐标与 bbox 中心混淆也成立。区域接口可以降低提取错误，但当前工具没有自动解决长面板中的子区域，仍有裁掉独立部件却不报警的负例。它解决“读取是什么”，不能保证模型用对“所以该怎么做”。保留为第二候选，不与控制表提示混测。
- **调度：** 不同池/单次分差和正式公开榜 31.16 都不能定位到调度浪费；隐藏逐游戏轨迹拿不到，当前没有优于上述可见机制的直接证据。先不改。
- **完整 actor/world model：** 比一个只记录已观察控制关系的小表更复杂，容易把未验证理论做成错误模拟器。先测最小的证据使用习惯，再决定是否值得添加通用 projector/transition helper。

当前完成的是本地机制诊断和候选设计；模型采用、跨游戏覆盖改善、公开/隐藏榜提分均未验证。
